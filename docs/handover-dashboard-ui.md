## 4. Rules the code must follow (short; full text in `plan/project_handover.md` section 1)
- **One place for everything (R2):** URLs only in `src/lib/routes.ts` (add the new ones: `/dashboard`, `/dashboard/[quizId]`, `.../responses`, `.../settings`, `.../preview`, `/account`); words in `src/content/` (dashboard words go to `src/content/dashboard/*.ts`; this is the decision taken in the website session instead of one big `strings.ts`); colors only from tokens; primitives only in `components/ui`; **one responsive component, never two copies**; files under about 300 lines; no dead code; strict TypeScript; no raw hex colors in components.
- **Tokens** (Tailwind 4, defined in `design-system.css`): `ink slate mute ink-2 ctrl line line-strong soft dash page tint steel danger danger-soft danger-line danger-ink`, e.g. `bg-dash text-ink border-line`. Dashboard page background is `dash` (#F4F6F8), website is `page`. Font: add `font-inter` on the layout root. Breakpoint `nav` = 900 px (`nav:`, `max-nav:`).
- **Dashboard look differs from the website:** buttons and inputs are **10 px rounded** (website: pill). Add a `shape="box"` option to `Button` instead of a second component. Touch targets at least 44 px. Focus ring: 3 px slate outline, 2 px offset, always visible with the keyboard. Never use color alone for a state. Check `UIFoundations` for sizes.
- **Motion and hover (decided after the owner's review, details in handover section 3 "Motion"):** move only `translate`/`opacity`/`transform`; no animated `box-shadow`; lifts use the shared `.lift` class (no flicker at the edge); **Tailwind 4 moves things with `translate`, so every `transition-*` that moves something must list `translate`** (a `transition-[transform]` makes the hover jump); link underlines fade with `textLink`; open/close panels use a `grid-template-rows` transition; everything stops under `prefers-reduced-motion`. The owner asked that all of it is smooth **and lightweight**.
- **Text:** all built-in text is fixed English and never part of the Edit with AI data. Text the owner types can be any language.
- **Logged-out people** who open a dashboard URL go to `/login` (no `next` target yet; the real one is Phase 4: only same-site relative paths).
- Tests: Vitest for pure logic (the repo has Vitest configured only for DB tests; add `vitest.config.ts` for unit tests, keep `vitest.db.config.ts` as it is). Playwright comes in Phase 2.12.

## 5. Decisions to take in your first hour (write the answer into `plan/project_structure.md`)
1. **How mock data works.** `plan/project_handover.md` 4.3 says UI pages call repository interfaces (`src/server/repos/ports.ts`) and a mock implementation keeps state in `localStorage` or a cookie so a refresh keeps edits. Server components cannot read `localStorage`. Recommendation: make the interfaces **async**, write the mock implementation to run **in the browser** (store + `localStorage`, behind a small `RepoProvider`/hooks layer such as `useQuizzes()`), build the dashboard screens as client components that talk only to those hooks, and let Phase 5 replace the hooks' insides with server actions. The mock must use the **same** `lib/` functions as the real code: plan limits (`lib/plan/limits.ts`: 5 quizzes, 15 pages, 500 responses), slug rules (`lib/slug.ts`), `format.ts` ("Edited 2 days ago"). Decide, record, move on; ask the owner only if you find a real conflict with what they see.
2. **Layout:** route group `src/app/(app)/` with a layout (header: logo to `/dashboard`, "My quizzes", the reused `AccountMenu`; phone gate `DashPhone`; suspended-person dialog from `DashErrors`). The admin layout and the quiz layout come in later slices.
3. **Dev switches** for states that are hard to reach (limit reached, empty list, suspended, offline, "couldn't load"): put them on `/dev`, not in the real UI.
